# 记忆中枢底座接口 v1

本文件描述 `0.1.0` 中已经实现的 P0 协议。以 `src/core` 和 `src/runtime.js` 为运行依据。

## 组件与边界

| 组件 | 职责 | 来源文件 |
| --- | --- | --- |
| HostAdapter | 宿主就绪、聊天身份、消息版本、保存和事件解绑 | `src/host/sillytavern.js` |
| FactStore | 唯一事实日志、版本、事务、备份和重放 | `src/core/store.js`、`protocol.js` |
| TaskScheduler | 并发、去重、依赖、取消、超时和重试 | `src/core/scheduler.js` |
| ModelGateway | 主 API 与独立渠道的请求与队列接入 | `src/core/gateway.js` |
| Settings / Vault | 无凭据配置、渠道路由与会话凭据 | `src/core/settings.js` |
| Runtime | 生命周期、消息同步、聊天隔离和提交校验 | `src/runtime.js` |
| Diagnostics | 脱敏日志与基础操作面板 | `src/core/logger.js`、`src/ui/panel.js` |

后续模块可以维护可重建的缓存，但不能另存一份权威人物、物品或 RPG 状态。模块的持久事实均提交到同一 FactStore。

## 身份与持久化

聊天元数据的 `st_memory_core` 存储以下结构：

```json
{
  "schemaVersion": 1,
  "storeId": "chat_<uuid>",
  "scopeKey": "[\"character:avatar.png\",\"chat-file-id\"]",
  "revision": 0,
  "journal": [],
  "checkpoints": []
}
```

- 角色按头像文件身份区分；群聊按群 ID 区分。显示名称不参与身份判断。
- 聊天按宿主 `getCurrentChatId()` 区分。复制元数据到新聊天时分配新 `storeId`，记录 `forkedFrom`，继承的日志仍可重放。
- 每条消息在顶层保存 `st_memory_core_id: message_<uuid>`。删除前面的楼层不会改变剩余消息身份；复制产生的重复 ID 会修复。
- 消息版本为 `version_<swipeId>_<SHA-256({text,role})>`。编辑同一楼、重生成正文或切换 swipe 都会改变版本；切回原版本可重新激活对应事件。
- 消息记录只保存 ID、版本、正文哈希、角色、swipe 与当前位置。事实库不重复保存原始正文。

日志只包含两种记录：`messages` 表示当前有效消息列表；`changes` 表示一组事实操作。每个追加记录对应连续版本。检查点不增加日志版本。

## 事务协议

内部模块先 `await runtime.sync()`，再捕获一次提交依据；耗时任务结束后仍使用这次依据。

```javascript
await runtime.sync();
const lease = runtime.capture();
const source = runtime.getSnapshot().messages.at(-1);
await runtime.commit({
  idempotencyKey: `extract:${source.id}:${source.versionId}:schema-v1`,
  origin: 'model',
  evidence: [{ messageId: source.id, versionId: source.versionId }],
  dependsOn: [],
  ops: [{
    type: 'create', entityId: 'character_<uuid>', entityKind: 'character',
    name: '旅人', aliases: ['阿旅'], fields: { hp: 10 }
  }]
}, lease, signal);
```

`lease` 包含聊天作用域、运行时世代、事实版本和正文签名。切聊天、恢复历史、事实版本推进、正文改变或取消都会使旧任务的提交失败。正文未完成同步时不能捕获新的依据。

`origin` 为 `human / model / system / import`。模型变更至少携带一条当前有效的正文版本依据；派生事件还应使用 `dependsOn` 声明前置事实事件，防止前置事件失效后仍应用其结果。

| 操作 | 字段 | 规则 |
| --- | --- | --- |
| `create` | entityId、entityKind、name、aliases、fields | 同一有效状态中实体 ID 不重复 |
| `remove` | entityId | 移除实体及其字段锁 |
| `set` | entityId、path、value | path 为字段路径字符串数组；只修改 fields |
| `unset` | entityId、path | 移除对应字段 |
| `increment` | entityId、path、amount | 目标与结果必须为有限数字 |
| `lock / unlock` | entityId、path | 只有 human 可修改锁；祖先、子字段路径都受保护 |

所有输入必须为普通 JSON，拒绝原型字段、非有限数字、函数和特殊对象。先验证整组操作，再保存候选文档，成功后发布变更。保存失败不公布半份事务。

相同幂等键、相同操作和来源只提交一次；相同键对应不同内容时报 `IDEMPOTENCY_CONFLICT`。模块的键应绑定业务事件身份，不能每次重试重新随机生成。FactStore 可识别旧版本请求的已提交重复项；Runtime 的旧 lease 会先被拒绝，模块重新同步后可用同一幂等键核对结果。

## 重放、编辑与人工锁

查询任一历史版本时，先得到当时有效的消息版本，再按顺序重放其有效事实变更。来源失效或依赖失效的整组变更被跳过，并在 `skipped` 中保留原因。事件没有被物理删除，历史查询可解释其来源。

人工更正可直接写字段，模型和 system/import 写入必须遵守人工锁。P0 不自动把所有人工修改变成锁；需要保护时在同一事务中明确添加 `lock`。锁不会阻止人工继续修改。

P0 已提供状态失效和重放原语。摘要视图、召回缓存、RPG 和表格等实际模块将在对应阶段订阅事件并接入，不能因此把尚未实现的视图记为验收完成。

## 调度与 API

```javascript
const job = runtime.scheduler.submit({
  key: '业务键', module: 'core', scope: lease.scope,
  dependsOn: [], timeoutMs: 60000, retries: 2,
  retryable: error => error.code === 'RATE_LIMIT',
  isCurrent: () => { try { runtime.assertLease(lease); return true; } catch { return false; } },
  run: async ({ signal, assertCurrent, attempt }) => {
    assertCurrent();
    // 执行异步工作后再次校验，并通过 runtime.commit(..., lease, signal) 提交。
    return { attempt };
  }
});
await job.promise;
```

默认并发 2，构造参数允许 1–8。仅对尚在排队、运行或退避的相同 key/module/scope 去重；终态任务可以重新运行。依赖失败时后置任务不执行。重试次数最多 5，使用指数退避，单次等待最多 30 秒；API 的 429 支持 `Retry-After`。

任务取消和超时会立即释放队列占用。异步代码仍须使用 `signal` 和提交校验；底座不能阻止任意插件代码绕过协议自行写入宿主数据。

默认路由优先级为：聊天的任务覆盖 → 角色的任务覆盖 → 全局任务路由 → 全局默认。聊天覆盖键为 `identity.scopeKey`，角色覆盖键为 `identity.characterKey`。配置可通过 JSON 导入设置；P0 面板提供全局默认渠道选择。

独立渠道只支持 OpenAI Chat Completions 兼容协议，通过酒馆代理发送，使用独立 `reverse_proxy / proxy_password`，不读取主 API 的密钥。依据为 [SillyTavern 代理实现](https://github.com/SillyTavern/SillyTavern/blob/release/src/endpoints/backends/chat-completions.js)。其他服务的原生协议属于后续 API 模块。

主渠道使用宿主 `generateRaw`，没有可用的取消信号接口：取消后底层请求可能继续，但响应不会继续成功发布。独立渠道使用 fetch 的 AbortSignal。P0 不提供主 API 的结构化输出约束，也不执行记忆提取提示词。

配置协议为版本 1，密钥只在 CredentialVault 内存中。支持明确的本插件版本 0 配置 `{schemaVersion:0, enabled:boolean}` 升级，并在宿主配置中保留 `st_memory_core_migration_backup`。不支持三款旧插件的配置或数据直接迁移；未知版本拒绝加载。

## 公共只读 API

`window.STMemoryCore` 的 API 版本为 1：

- `getCapabilities()`：版本、可用模块、宿主能力和保存边界。
- `getSnapshot({revision?})`：当前或历史状态、消息、已应用事件、失效记录与覆盖信息。
- `getHistory({after=0, limit=100})`：事件日志；limit 为 1–1000。
- `getSettings()`：无凭据配置副本。
- `subscribe(listener)`：返回取消订阅函数。观察者异常不影响事实提交。

主要事件包括 `store.changed`、`chat.ready`、`chat.empty`、`tasks.changed`、`settings.changed`、`generation.started`、`log.added`、`runtime.error` 和 `runtime.stopped`。

事实抽取模块应处理 `store.changed` 中 `reason:messages` 的有效版本变动；不要用所有运行时通知启动抽取。`generation.started` 必须检查 generationType，内部 quiet 和用户代写不会启动正文处理。正文版本没有变化的同步不会重复发布 `store.changed` 或 `chat.ready`。

覆盖信息始终明确声明 P0 尚未提取记忆：`complete:false / P0_NO_MEMORY_EXTRACTION`。正文未同步时为 `SOURCE_UNSYNCED`；没有聊天时为 `NO_CHAT`。不能把空实体列表解释为已覆盖所有正文。

## 已知边界

服务端无 CAS、跨设备并发、超大日志压缩、旧格式迁移和记忆模块均未实现。SHA-256 备份校验用于发现损坏，不是签名或访问控制。检查点是可校验快照，当前读取仍通过事件重放，没有性能加速承诺。
